The number-one way one-month builds die

Meet the enemy: scope creep

A real Week-6 story · LinguaLoop
  • Passed the gate with a language-flashcard app
  • Sponsor: "add video calls… add a marketplace… add a social feed"
  • Team feels pressure to say yes to everything
  • One month later: five half-built features, nothing ships
What this actually is

Scope creep — not "iteration."

New requests aren't bad. Saying yes to all of them mid-build is what kills the timeline. The cure isn't refusing people — it's a locked scope you can point to.

The trap "The sponsor is paying, so we must add it." No. Your job is to ship one thing that works, then decide what's next — with the sponsor, on the record.
🇹🇭 Scope creep = งานบวมขึ้นเรื่อย ๆ จนไม่เสร็จสักอย่าง วิธีแก้ไม่ใช่ปฏิเสธคน แต่คือมี ขอบเขตที่ล็อกไว้ ให้ชี้ได้

The tool · MoSCoW

Locking scope = drawing four lines

MUST

Ship or fail

Your one core workflow. If this isn't done, there is no product. Keep it small.

SHOULD

Important, not vital

Adds real value — but the product still works without it. Only if Musts are done.

COULD

Nice to have

Do it only if there's spare time. First to be dropped.

WON'T

Not this build

Written down, on purpose. The video calls, the marketplace — parked, not forgotten.

Example · a food-delivery app MUST place an order · SHOULD track the driver live · COULD rate the restaurant · WON'T in-app chat with the driver. Same app, four honest verdicts — no feature is "bad," each just has a place.
The point of the WON'T list Scope lock isn't just picking what to build — it's explicitly naming what you will not build this month, so no one has to argue about it again mid-sprint.
🇹🇭 หัวใจอยู่ที่ช่อง WON'T — เขียนสิ่งที่ "จะไม่ทำเดือนนี้" ให้ชัด จะได้ไม่ต้องมาเถียงกันซ้ำกลางสปรินต์

How to actually lock it

The one-workflow rule

Do this
  • Pick the single workflow a real user completes end to end
  • Trace it: it must answer a validated pain from the gate
  • Everything else → Should / Could / Won't
  • Write the locked list where the whole team sees it
CupLog · locked
  • MUST — log a cup in ≤3 taps · see today's total
  • SHOULD — edit a mistaken entry
  • COULD — export the day as CSV
  • WON'T — multi-café, payroll, inventory, accounts
Test it · one breath Read your MUST list aloud in one breath.
❌ Too big: "log a cup, edit it, export CSV, see weekly charts, and sync across cafés."
✅ Locked: "log a cup in ≤3 taps and see today's total." Everything cut just moved to Should / Could / Won't — nothing was thrown away.

The sponsor keeps asking · what to say

Not "yes." Not "no." — "Not now, and it's recorded."

Weak responses
  • "Sure!" → scope creep, timeline dies
  • "No." → damages the relationship
  • Silently ignore it → sponsor loses trust
  • Pause the build until requests stop → they never stop
The engineer's move
  • "Great idea — it goes on the Could / Won't list for this build."
  • Record it in the backlog as out-of-scope (this sprint)
  • Keep the one MUST workflow locked
  • Revisit the parked list after Alpha (W8)
💡 In plain terms You don't reject the sponsor — you reject doing it right now. A written "not this build" is a promise you'll come back to it, not a rejection.

Before the first feature · Sprint 0

Sprint 0 = build the foundations, not the features

Sprint 0 IS
  • Setup before feature sprints start
  • Repo, project board, branches, environment
  • The agent's rulebook: CLAUDE.md + rule.md
  • A "definition of done" everyone agrees on
Sprint 0 is NOT
  • Shipping the first paid version
  • Final user-acceptance testing
  • Writing the launch / marketing plan
  • Building features already (that's W7+)
Why it matters Teams that skip Sprint 0 and "just start coding" spend week 7 fixing their own setup. One clean day now buys you three clean weeks.
🇹🇭 ทีมที่ข้าม Sprint 0 แล้วรีบโค้ด มักเสียเวลาสัปดาห์ 7 ไปแก้ระบบตัวเอง · ลงทุน 1 วันวันนี้ ได้คืนมา 3 สัปดาห์

The enabler · Model Context Protocol

MCP gives your agent hands and eyes

What it is
  • A standard way for an AI agent to connect to external tools & data
  • Turns "a chatbot that talks" into "an agent that acts" — reads your repo, opens a browser, queries a database
  • One protocol, many servers (GitHub, browser, docs, files…)
What it is NOT
  • Not a faster compiler
  • Not a replacement for Git / version control
  • Not "automatic PDPA encryption"
💡 In plain terms Without MCP, the agent can only describe what to do. With MCP, it can reach into your real tools and do it — across the whole SDLC, not only coding.
🇹🇭 ไม่มี MCP = เอเจนต์ได้แค่ "บอกวิธี" · มี MCP = เอเจนต์ "ลงมือทำ" กับเครื่องมือจริงของเราได้เลย

MCP · the shape of it

One agent → one protocol → many tools

Today you connect one Start with GitHub MCP — it plugs the agent straight into the repo and board you set up in Sprint 0. Add browser / docs later as the build needs them.

MCP · one real moment

Same question — with and without MCP

Without MCP

You: "List the open issues on our repo and tell me which are done."

Agent: "I can't see your GitHub. Paste the issue list here and I'll help." → you copy-paste by hand, every time.

With GitHub MCP

Same prompt. The agent reads your board itself and answers:

# issues on CupLog · read live via MCP
#12  Log a cup in ≤3 taps      open
#13  Show today's total        open
#14  Set up .gitignore         done → ready to close ✔
The difference Nothing about the prompt changed — the agent's reach did. That is the whole point of MCP: same conversation, real hands.

Moving fast ≠ no rules

BUILD does not cancel Week 2

Tempting, and wrong
  • "Coding started — delete rule.md."
  • Hide which parts the AI wrote
  • Skip PDPA "until it works"
  • Stop caring about consent / logs
What you actually do

  • Disclose your AI use — it's a strength, not a secret
  • PDPA / CCA §26 / ETA stay binding in BUILD
  • Stay inside your governance rules as you speed up
Link to W2 The faster the agent moves, the more your rule.md earns its place — it's what keeps a fast build legal and honest.

One decision the lock makes for you

Locked scope → the simplest architecture that works

Justified by a one-workflow, one-month build
  • A single, well-structured app (a "modular monolith")
  • A managed backend / database — don't run your own
  • One clear seam around the core workflow (recall W4)
Not justified — this month
  • Microservices for a 5-person, 1-month project
  • Custom infra you have to babysit
  • Architecture "for scale you don't have yet"
The principle Scope drives architecture. You locked scope to one workflow — so the right architecture is the smallest one that ships it well, not the most impressive one.
