The one sentence

A good requirement is one your team and an AI agent understand the same way. Not just something a human understands

Two kinds of requirement

What it does vs. how well it does it

Functional

What the system does

  • A user can perform a real action
  • Written as a user story: As a…, I want…, so that…
  • Example: "record a coffee's score + flavor tags"
Non-functional (NFR)

How well it does it

  • Usability, performance, reliability — measurable
  • "Fast" is not a requirement. "<2 seconds" is.
  • If you can't measure it, you can't test it

Format · worked example CupLog §4.2

User story + INVEST + MoSCoW

As a [user], I want [X], so that [Y] — Independent, Negotiable, Valuable, Estimable, Small, Testable.

#As a…I want to…so that…Priority
F1baristarecord a score (1–10) + flavor tagsmy notes aren't lost (P1)Must
F2baristasee a list of past cuppingsI can compare batches (P2)Must
F3baristapick from a shared flavor-tag listwe score consistently (P3)Must
F4owneradd a coffee (name, batch, date)cuppings attach to the right coffeeMust
F5baristafilter/sort cuppings by score/coffeeI find the best batch fastShould
F6ownerexport the history (CSV)I can share with buyersCould

Why is F5 a Should, not a Must? It's not the one core workflow (F1) — the thing month-2 BUILD must ship end-to-end.

NFRs that are actually measurable

Time, count, % — not "fast" or "good"

NFR1 Usability

< 60 seconds

A barista can log one cupping in under 60 seconds.

NFR2 Performance

< 2 seconds

The history list loads in under 2 seconds for 200 cuppings.

NFR3 Reliability

No data loss

No data loss if the phone loses signal mid-save (queue + retry).

An NFR you cannot measure fails the exam. "The system must be fast" is not a requirement.

Prioritization

MoSCoW — order the backlog, don't just list it

Must

Breaks without it

The core workflow doesn't function. Ships in month 2 (BUILD).

Should

Important, not core

Real value, but the workflow survives without it for now.

Could

Nice if time allows

No harm if it never ships this phase.

Won't

Out of scope

Explicitly not this phase — write it down so no one assumes it's coming.

CupLog's month-2 commitment: B1–B5 (Must only). B6–B7 (Should/Could) only if time allows.

The rule that gets checked at the Gate

Every requirement traces back to a real pain

Traceability chain pain → requirement → backlog item
InterviewP1 — "tasting notes on paper/LINE get lost"
RequirementF1 — "As a barista, I want to record a score + tags, so that my notes aren't lost"
BacklogB1 — "Record score + flavor tags for a coffee" — Traces to: F1, P1

No requirement that's just "made up" with no source. The W5 Gate checks whether your backlog is tied to real interview pain — not just whether a table exists.

What an AI agent actually is · STAG Ch.6.1, p.319

Five core components

1 Perception

Taking in input

Text, files, tool results, environment state — preprocessed before the model reasons about it.

2 Memory

Remembering

In-context (the prompt), external (files/DB), episodic (past actions) — layered for long tasks.

3 Planning

Breaking down the goal

Splits a complex goal into subtasks, handles dependencies between steps.

4 Action

Doing it

Calls tools, directs other subagents, reads/writes files, reports to the user.

5 Self-evaluation

Checking itself

Did the action work? Retry, adjust, continue, or stop — and report progress/errors.

The difference from a chatbot: a chatbot answers once. An agent loops through these five steps until the task is actually done.

FileScopeWhen it loads

Skill (SKILL.md)A specific task/procedureOnly when invoked with /skill-name — saves context
SubagentA specialist persona + its own toolsDelegated to by Claude, or @-mentioned — separate context

Walking the room

Two failure patterns to catch

Catch this

Agent instructions with no "ask if unsure" line

  • The agent will guess instead of asking
  • Fix: add "if anything is unclear, ask and offer ≥3 options" to the subagent file
Catch this

Requirements with no traced pain

  • A requirement invented on the spot, not from an interview
  • Fix: send them back to their interview notes before writing F-items

Appendix · the one workflow to remember

edit → add → commit → push

  • 1Edit — change a file locally (spec, backlog, an agent file)
  • 2git add . — stage what changed
  • 3git commit -m "…" — record it with a message
  • 4git push — send it to GitHub so the team and the grader can see it

Do this every time you or an agent changes a file under .claude/ or .docs/ — a spec that only exists on one laptop doesn't count at the Gate.
