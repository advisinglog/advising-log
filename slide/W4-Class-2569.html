Rule of the day: every one of these describes the same one core workflow. If your diagrams, journey and prototype disagree, you lose marks — consistency is the whole game.

The one thing that earns marks

One core workflow — everything agrees

Pick one core workflow (for CupLog: "Record a cupping"). Every artifact must trace back to it and to a requirement.

pain (interview)→ user story F1→ feature "Record a cupping"→ journey 5 steps→ D1–D4 diagrams→ prototype screen
Earns marks
  • Same actor names everywhere
  • Diagram flow = user-journey = requirement
  • Architecture matches the tech stack you named
Loses marks
  • Diagram copied from a blank template
  • Actors / labels not in your spec
  • Journey says one thing, D4 another

💡 In plain terms Pick one task and follow it like a single thread through every document. If the thread breaks — a diagram shows a step your journey doesn't — you lose marks. Example: pain "I lose my cupping notes" → story F1 → feature "Record a cupping" → 5-step journey → D4 → the New-cupping screen. One thread, six documents.

D1 · System Context

The system as one box

What earns the mark
  • The system is one box — no inside detail
  • ≥ 2 external actors, named as in your spec
  • Scope is obvious: what's in, what's out

💡 Read it Draw the app as one box, plus everyone/everything outside that talks to it. No insides yet — just the boundary. Here: the CupLog box, the Barista & Owner who use it, and where the data is stored.

Agent prompt: "Draw D1 System Context for CupLog from the spec — system + external actors + stored data only. Output mermaid."

D2 · Use Case / User Story Map

Who can do what

What earns the mark
  • Every actor is linked to its use cases
  • The core use case is present & central
  • include/extend used only when real (record «includes» consent)

💡 Read it Stick people (actors) linked to bubbles (things they can do). Here: the Barista can "Record a cupping"; recording always includes "Give consent".

UML notation: actors = stick figures · use cases = ovals inside the system box · actor–use-case = plain solid line (no arrowhead) · «include»/«extend» = dashed line, open arrowhead. A User Story Map is an accepted alternative — pick what fits your product (chatbot vs. CRUD vs. ranking).

D3 · High-level Architecture

Boxes, layers, and the data direction

What earns the mark
  • Layers/components, not code — high level
  • Arrows show data / call direction
  • Agrees with your tech stack named in §5

💡 Read it The parts inside and which way data moves: phone → server → database. Boxes are parts; arrows mean "who calls whom". Here: the web app calls a REST API, which reads/writes the database.

The rule.md duties surface here: an access_log table (CCA §26) and a consent store (PDPA) belong in this picture.

D4 · Activity / Sequence

One scenario, start to end

💡 Read it: one task as a flowchart with real UML dots — start ● → steps → a diamond ◆ where it decides → end ◉. Here: saving a score, with an "Online?" branch.

What earns the mark
  • UML nodes, not boxes: ● initial → actions → ◉ final (never a labelled "Start"/"End" box)
  • Decision & merge = diamond; branches rejoin at a merge before the final
  • Steps = the user-journey (same order); guards in [brackets]

A sequence diagram (lifelines · activation bars · solid call / dashed return) is an accepted alternative for message-heavy flows (e.g. a chatbot).

This is the DISCOVER-phase version of a feedback loop: the design checks itself, you fix the doc, not the diagram-of-record.

Step 4 · the new piece today

What is a Design System — and why agentic?

A design system = your product's reusable visual rules: tokens (color, type, spacing, radius) + component rules (buttons, chips, cards). Define it once; every screen obeys it.

Without a system
  • Every screen invents its own colors/spacing
  • The agent guesses → inconsistent prototype
  • Hard to review, harder to build
With design-system.md
  • The agent reads it and builds consistent screens
  • It's a UI Skill — same idea as CLAUDE.md/skills
  • Change a token once → whole prototype updates

💡 In plain terms A design system is a style guide the AI can actually follow: the exact colors, sizes and rules, written down once. Example: "primary button = accent color, buttons ≥ 44px" — so every screen the agent draws matches.

Playbook link: design-system.md is to UI what rule.md is to law — institutional knowledge the agent applies every time it draws a screen.
