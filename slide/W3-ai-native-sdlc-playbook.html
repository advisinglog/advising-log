How to transform the software development lifecycle with AI — stage by stage. Code is no longer the bottleneck; the process around it is.

6 stages · looped, not linear Source: claude.com/blog · Aug 2026 Teaching pack · Dr. Prasara Jakkaew, ADT MFU

The core shift

Code is no longer the bottleneck

The classic SDLC was designed when writing code was the slowest, most expensive step. With agentic AI, build collapses to hours — so the human-speed stages around it become the constraint.

Build collapses to hours — so the effort (and the risk) shifts to the steps left and right of it.

Two operating models

Traditional vs. AI-Native SDLC

Traditional
  • Linear, phase-gated with discrete ownership
  • Process-heavy controls; human execution at every step
  • Sign-offs & handoffs between specialised roles
  • Governance discovered in reviews, weeks later
AI-Native
  • Looped, continuous; AI embedded at each stage
  • Automated handoffs trigger the next phase
  • Human judgment concentrated at decision gates
  • Governance enforced as AI acts; audit trail in commits

Big idea: every stage produces a machine-readable, version-controlled artifact (a markdown file). Artifacts replace committees; the commit chain is the audit trail.

The shape of the process

It's a loop, not a line

Each stage commits an artifact the next one reads. The chain bends back on itself — production feeds new intent.

Stage 1 · Plan

Capture intent as intent.md

Ideas die in meetings and refinement cycles. Instead, the originator brainstorms with Claude in natural language until concrete, then commits a markdown file.

Flow
  • Describe the problem to Claude
  • Brainstorm scope, users, constraints, success metrics
  • Claude writes intent.md from your template
  • Commit → product owner approves or rejects

intent.md

# Intent: claims status self-service
Author: J. Ortiz (claims ops). Status: draft.

## Problem
Handlers spend ~1/3 of call time on
status-only queries.

## Proposed outcome
Customers see status, next step, date in portal.

## Constraints
No new PII in session. Existing auth only.

## Open questions
Do third-party adjusters need access too?

Metric — Leading: time from first conversation to committed intent (hours, not weeks). Lagging: survival rate of intents accepted into Stage 2.

Stage 2 · Design

Requirements & design collapse into spec.md

Product owner loads organizational skills (brand, security, compliance, UX), attaches the approved intent, and asks Claude to produce a full spec — with conflicts flagged.

The prompt pattern

"Read the attached intent.md and produce a requirements & design spec for our codebase. Apply the skills available to you so the plan conforms to our brand, security and UX standards. Document it fully as spec.md, ready for engineering."

Why it matters
  • Policy applied live, as the spec is written — not discovered weeks later
  • Flagged concerns routed to policy owners first
  • Spec, prompt & skill versions all logged

Metric — Leading: elapsed time intent → spec. Lagging: requirements rework after build starts.

Stage 3 · Build · Play 3a

Nothing implemented without an approved plan.md

Claude Code plan mode is read-only: it cannot edit files until the engineer accepts the plan. Design review happens on a document — far cheaper to change than code.

plan.md

# Plan: claims status self-service

## Files that change
StatusPanel.tsx (new), routes/status.py,
tests/test_status.py

## Order of work
1. Add status endpoint behind existing auth
2. Panel against the endpoint
3. Wire into portal nav

## Risks
claims-core API rate-limits at 50 rps; cache.

## Proof
test_status.py covers four claim states.
Interrogate the plan
  • What could break? What's riskiest?
  • What alternatives were discarded?
  • Iterate until a stranger could implement it
  • If code departs from plan → update plan.md in the same commit

Auto mode (3b): once guardrails mature, approve the plan once and let Claude apply changes without per-edit prompts — review shifts to artifacts after longer autonomous sessions.

Stage 3 · Build · Plays 3c–3d

Institutional knowledge: CLAUDE.md & Skills

CLAUDE.md · read every session start
  • Build / test / lint commands + healthy output
  • Conventions & architecture that matter
  • Common mistakes Claude keeps making

Rule: when Claude gets it wrong twice, the correction goes in CLAUDE.md. Keep it under one page.

Skills · applied consistently across sessions
  • For policy enforced inconsistently today (security, API, brand)
  • Applied broadly; updated centrally
  • Folder .claude/skills/<name>/SKILL.md
  • Distributed via plugin marketplace
# CLAUDE.md — Payments service
## Conventions
- Money is always BigDecimal, never double.
## Things Claude gets wrong
- Do not bump dependency versions; platform team owns them.
- Legacy v1/ package is frozen; changes go in v2/.

Stage 3 · Build · Plays 3e–3f

Hooks & parallel sessions

Hooks · deterministic guardrails
  • Back any must-hold skill with a hook
  • Block edits to protected / frozen paths
  • Run formatter/linter after each edit
  • Keep credentials out of diffs

Build-phase hooks stay fast & scoped. Heavy checks → commit/PR. Approvals → Stage 5.

Parallel sessions & subagents
  • One engineer orchestrates many streams
  • Each Claude session in its own git worktree
  • Start with 2–3; scale with review capacity
  • Subagents (.claude/agents/) = scoped helpers with own context

The pitfall: don't use hooks as approval gates during build — that puts a human back on the critical path. Hooks block; gates ask (Stage 5).

Stage 4 · Test

Every session checks its own work

Late signals (CI minutes later, prod weeks later) force humans to review everything. Give Claude a feedback loop so it verifies before you ever see the diff.

Play 4a · feedback loop
  • Wrap checks in one target that exits non-zero
  • State a quantifiable "done" Claude checks itself
  • Bug fix → write the failing test first; hook blocks editing tests during the fix
  • UI → give it a browser + mock; iterate 2–3 rounds
Play 4b · continuous evals in CI
  • 20–50 real tasks with accepted outcomes
  • Runs when CLAUDE.md / skills / hooks change
  • Gate config changes on pass rate
  • Every incident → a permanent regression eval

Make verification part of "done": put "run build, test, lint and paste the output before reporting complete — fix the code, not the test" directly in CLAUDE.md.

Stage 5 · Deploy

Review runs both directions; the gate stays human

The agent does everything up to the production gate — and nothing past it. Separation of duties is enforced by permissions and hooks, not by trust.

5a · PR review loop

Claude gives and receives reviews. Policy lives in REVIEW.md (bugs / security / compliance passes; Important vs. Nit). Humans still approve via branch protection.

5b · hooks as approval gates

A hook can ask — pausing until a named person authorizes (e.g. release). Non-negotiable gates live in managed settings engineers can't disable.

5c · managed settings

For regulated orgs: deny secret reads, sandbox with domain allowlist, managed-hooks-only, approved marketplaces, minimum version. Pushed via MDM.

5d · CI/CD integration

Start read-only (triage builds). Writes arrive as PRs. Tier autonomy by env: dev deploys freely, prod needs a release manager. Rehearse rollback.

Stage 5 · the gate in code

Governance enforced as AI acts

.claude/hooks/production-gate.sh

#!/bin/bash
# Prod deploys need release authorization
cmd=$(jq -r '.tool_input.command')
if [[ "$cmd" == *"deploy"* && \
      "$cmd" == *"production"* ]]; then
  if [ -z "$RELEASE_APPROVAL" ]; then
    echo "Needs release authorization." >&2
    exit 2  # exit 2 blocks; msg → Claude
  fi
fi
exit 0
Separation of duties
  • Write: Claude produces artifacts, code, PRs
  • Review: humans judge intent & risk
  • Approve: humans hold each gate — spec, plan, PR, release
  • Monitor: agents watch prod; humans triage

The writing agent has no approval path. Every allow/block is logged with a timestamp.

Stage 6 · Maintain

The loop closes

A trigger invokes Claude with no person in the invocation path. Findings re-enter the pipeline as a new intent.md — the cycle feeds itself.

Detection → response tiers
  • Detection is deterministic — no model (baselines, Western Electric rules)
  • 1σ → log only
  • 2σ → Claude diagnoses, read-only
  • 3σ → Claude may act, only via PR or a pre-approved runbook

bands.yaml

metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request,
                     runbook:rollback-deploy] }

Claude on call (6b): via Claude Tag in Slack/Teams, Claude is first responder in-channel — diagnosis, authorization and fix stay where the incident happened. The channel is the audit record.

The through-line

Every stage commits an artifact the next stage reads

intent.md
Plan → spec.md
Design → plan.md + code
Build → test output
Test → review findings
Deploy ↻ new intent.md
Maintain

Together, the intent, the spec, the plan, the diff and the review findings are the audit trail. No parallel tracking system required.

Artifacts over meetings

Markdown, version-controlled, replaces committee decisions.

Automation over habit

Skills, hooks & config enforce policy; humans do judgment.

Continuous over gated

Feedback loops, tests & evals run every session.

Closed-loop over reactive

Production findings return as new intent.

Adoption

Start small, one loop at a time

Two "clay plays" have no dependencies — start there: intent capture and CLAUDE.md. Everything else builds on the artifact before it.

Weeks 1–4

Intent

Stand up an intent repo + template; product owners capture ideas as intent.md.

Weeks 5–8

Plan mode

Write CLAUDE.md; run Claude Code in plan mode; commit plan.md.

Weeks 9–12

Feedback

Verification loops + continuous evals; tune CLAUDE.md from learnings.

Weeks 13–16

Review

Enable managed code review; first security skills; approval-gate hooks.

Months 5–6

CI/CD

Non-interactive diagnostics; rollback rehearsal.

Month 6+

Closed loop

Autonomous maintenance agent; incident response feeds itself.

Bridge · Week 2 → the playbook

rule.md — your team's legal skill

In the playbook, policy that must apply consistently becomes a Skill or lives in CLAUDE.md. In our course that policy is Thai law — and your file for it is rule.md, committed at repo root next to CLAUDE.md.

rule.md — loaded by the AI agent, like a compliance skill

# rule.md — CupLog legal rules

## PDPA — personal data
If the system stores a barista's name or email,
it must capture consent first and provide a
delete-within-7-days option (erasure right).
Never paste raw interview transcripts to a public LLM.

## Computer Crime Act §26 — logging
If the system has login, it must keep access logs
for at least 90 days (who / when / what).

## Electronic Transactions Act §9/26/28 — e-evidence
If a user clicks "I agree", store a timestamp,
the text version agreed to, and the user id.
Write rules as commands, not descriptions
  • Pattern: "If the system ___, it must ___"
  • Testable & agent-executable — not legal prose for humans
  • One file, many rules — cover login, storage, consent, confirm buttons

This is the playbook's Skills / CLAUDE.md idea (Play 3c–3d) applied to Thai law. It re-enters the loop at Stage 2 (org skills), Stage 3 (agent context) and Stage 5 (a compliance review pass in REVIEW.md).
